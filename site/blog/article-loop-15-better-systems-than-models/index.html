    システムはモデルを超える — GraphRAG検証データとエージェント3層設計¶

    元ファイル: グラフエンジニアリング.md, ハーネス、レイヤー、グラフ.md, 巨大モデルに勝る仕組み.md（すべて同じNotebookLM Notebook #ef53b959）

    概要¶

    Microsoft GraphRAGの実証テスト結果、Stanford大学のスケーリング則、AnthropicのClaude統合事例に裏打ちされた「良いシステム > 大きなモデル」という設計原則と、エージェントの3層アーキテクチャ（環境→フィードバック→フロー）を解説する。さらにGraph Engineeringの実践パターン（並列展開・信頼設計・コスト最適化）を追記した。

    パラダイムシフト : テキスト検索 → 現実検索（因果関係検索）¶

    RAGの限界¶

    通常のRAGはテキスト断片をキーワードマッチする。「3月の売上低下の理由？」のような複雑質問に対し、RAGは「3月」と「売上」を含む文書を抽出するだけで、根本的な因果連鎖を見つけられない。

    Graph Engineeringの優位性¶

    Graph Engineeringは「関係性（現実）」を検索する。同じデータ・モデルでも：

    倉庫の問題 → サプライヤ遅延 → ネガティブレビュー → 変換率23%低下 → 売上低下

    という因果連鎖を正確にたどれる。LLMは言葉を知るが、関係性を知るのはナレッジグラフである。

    Microsoft GraphRAG実証データ¶

    指標 RAG GraphRAG
    ローカル質問（特定エンティティ） 得意 得意
    グローバル質問（データセット全体のパターン） ❌失敗 ✅可能
    精度改善 − +18%
    トークンコスト/タスク − 85%削減（~$0.004/タスク）

    Microsoftの発見¶

    GraphRAGはローカル質問では既存手法と同程度の性能を出しながら、グローバル質問で初めて真価を発揮。従来の文書アプローチと比べて精度18%向上、コスト85%削減。

    Stanford DSPy / STORM 研究：スケーリング則の逆転¶

    Stanfordが示した核心的な発見：

    「巨大モデル + 粗悪グラフ」 < 「小規模モデル + 優れたグラフ」（常に）

    なぜ逆向きか？3つのポイント¶

    1. 「推測」→「明示的参照」へ¶

    通常のLLM/RAGは膨大なテキスト断片から関係性を推測する。良いグラフは情報を主語→関係→目的語のトリプルで保存。MIT KEPLER研究：明示的構造をアクセスできるモデルは論理エラーが格段に減る。

    2. モデルを「世界の中心」→「ノードの一つ」へ¶

    パイプラインをつながったモジュールのグラフとして扱う。「検索→推論→検証」「リサーチ→収集→構成→執筆→検証→修正」と構造化されたステップ。

    3. テキスト → の検索 → 因果関係 の検索¶

    小規模モデルでも「現実のつながり」をたどることで、巨大モデルでは見つからない深い洞察を導ける。

    グラフ最適化：直列チェーン→並列ノードへの変換¶

    ノードとエッジの正しく定義する¶

    多くの人は「Aを要約して、その次に天気を教えて」のように、データが交差しない処理まで直列に繋いでしまう。しかしデータが交差しないなら、それは独立したノードである。偽の依存関係（エッジ）を削除すると、直列チェーンは複数の独立並列ノードになる。

    明確な契約（スキーマ）¶

    並列化するには、各ノードに入出力の厳密なルール（JSONスキーマなど）を持たせることが必須。出力の形が決まっていなければ、それはノードではなく単なる会話である。

    配管作業にAIを使わない¶

    ノード同士の結果を「結合・重複排除」するような単純作業はAIではなく通常のプログラムコード（JavaScript等）で行うべき。エージェントは「判断」のために使うもの。「配管作業」に使えばコストの無駄。

    エージェント艦隊操作パターン¶

    ファンアウト（並列展開）¶

    複数の情報源やファイルを処理する際、一つずつ順番に処理するのではなく、同時に別々のエージェントを立ち上げて並列処理させる。これにより、1つのモデルのコンテキストウィンドウをパンクさせることなく、数十〜数百の処理をスケーリングできる。

    ファンイン（集約）とバリア¶

    並列処理した結果を一つにまとめる地点を「バリア（障壁）」と呼ぶ。バリアは「すべての結果が出揃うまで待つ」ため、本当に全体を見渡す必要がある処理（全体での重複排除や順位付け等）の時にだけ使用する。

    ダイヤモンド型の設計¶

    AIワークフローの王道は「分割（ファンアウト） → コードによるデータ整理（リデュース） → エージェントによる最終回答の生成（合成）」というダイヤモンド型。AIに次のステップをどう踏ませるかではなく、「どこでタスクを分割し、どこで統合するか」を設計することが重要。

    コードによる動的ルーティング¶

    例えば「変更の重要度」をAIモデルに判定させ、その結果（高・低）に基づいて「どのエージェントを起動するか」という分岐は、通常のプログラムコードで行う。「AIに判断させ、コードで行き先を決める」ことで、予測不能な動作を防ぐ。

    結果の信頼性を担保する設計¶

    エッジに検証者を配置する¶

    同じAIモデルに自身のミスをチェックさせても、同じ視点で間違えるため意味がない。必ず「別の検証エージェント」を配置し、敵対的な視点（反証を試みる）、異なるレンズ（正確性、安全性等）、または複数の裁判官による採点を行ってから次の処理へ進める。

    ノードの隔離¶

    並列処理中に1つのエージェントが失敗しても、全体が停止しないように設計。また、複数のエージェントが同じファイルを同時に書き換えないよう、個別のサンドボックスで実行させる。

    安全なループ構造（Loop until dry）¶

    未知のバグ探しなどでループ処理を行う場合、無限ループによるコスト爆発を防ぐ必要がある。「確認済みの結果」だけでなく「これまで見たすべての結果」と重複排除を行い、「K回連続で新しい発見がなければ停止する」という厳格な終了条件を設ける。

    コストと速度の最適化パターン¶

    適材適所のモデル配置¶

    すべてのノードで高価で賢いモデルを使う必要はない。単純なデータ抽出や分類には安価なモデルを使い、最終的な判断や要約（ファンインのノード）にのみ高価なモデルを使用することで、品質を落とさずにコストを削減できる。

    パイプラインとバリアの使い分け¶

    バリアはすべての処理の完了を待つので時間を浪費する。後のステップが全データを同時に必要としない限り、終わったものから順次次のステップへ流す「パイプライン処理」をデフォルトにすべき。

    グラフの動的生成¶

    事前に計画できない複雑なタスクの場合は、人間が手動でグラフを描くのではなく、Claude等のAI自身にオーケストレーション（進行管理）スクリプトを書かせ、動的にタスクを分割・並列化させることも可能。

    エージェントの3層アーキテクチャ設計パターン（Anthropic Claude検証）¶

    層 名前 シンボリックモデル 何を設計するか
    1 ハーネス（環境） → AIを囲む物理・設定・権限・ツール
    2 ループ（フィードバック） ...↻ 検証・反復サイクル。証拠で制御せよ
    3 グラフ（フロー制御） ┌─→┐↓ ワークフロートポロジー（順序/分岐/並列）

    ハーネス層 — AIの「身体」を構築する¶

    • コンテキスト注入: 指示、検索事実、会話状態
    • アクションサーフェス: API / ブラウザ / シェル / DB
    • 永続化: ファイル, チェックポイント, ロングメモリ
    • 実行制御: タイムアウト, リトライ, 予算管理
    • 安全性/ガバナンス: 権限, 分離, 機密情報取り扱い
    • 可観測性: ツール入出力, 状態遷移, コスト追跡

    ループ層 — フィードバックの反復¶

    重要な設計原則：「信頼」でなく「証拠」でループを回す。 テスト合格、レビュアー承認等の明確基準。ただし毎ループ追加はコスト増 → 失敗時の損害 > ループ検証コスト の時のみ追加。

    グラフ層 — ワークフローのトポロジー設計¶

    ノード（手順）とエッジ（許可ステップ）でワークフロー全体構造を明示設計。分岐、並列、承認プロセス、専門エージェント連携に不可欠。ただし、「3ツール+放任」のような単純タスクには不向き。最初のパスはハーネスだけ → 安定パターン確認後にグラフ化せよ。

    入れ子関係¶

    ハーネス（環境）
└── グラフ（ワークフロー）
    └── ループ（フィードバック）
        └── ツール/メモリ/検証
            └── モデル（LLM = 世界の中心ではない）

    ハーネスに詰込もうとするアンチパターン¶

    アンチパターン 症状 正しいアプローチ
    グラフを先に作る プロセスを過剰にノード化 まずシンプルなハーネス→安定後グラフ化
    コストリーク ループの停止条件がない 測定可能な目標/最大試行回数
    ハーネス詰込み ツール過多で選択ミス・混乱・セキュリティリスク コンテキストパック：最低限のパックのみ注入
    モデルのせいにする 古い状態データ/壊れたAPI→オーケストラ失敗をモデル限界と勘違い レイヤードデバッグ：どの層か特定してから修正

    デバッグパターン：どの層を直す？¶

    • ハーネス: エージェントが適切なデータアクセスできない or セッション跨ぎで記憶忘れる
    • ループ: 初め惜しいが信頼性低い or 成功後無駄に作業/証拠なし停止
    • グラフ: 複数専門エージェントを決められた順序で動かすが必要

    まとめ：Stanford / Microsoft / Anthropicの共通結論¶

    AIの最終出力はモデルの大きさや性能よりも、そのシステムの設計（グラフ構造）によって決まる。知識グラフを強力な土台に組み込んだ小規模モデルは、単独稼働の巨大モデルを超える。1000個のパラメータ > 5つのパラメータで構築されたシステム。（意訳：正しい設計 > モデルサイズ)

    また「プロンプトを書く人は質問をするが、アーキテクトはグラフを描く。」直列エージェント（次々にステップを踏ませる）は初期のやり方であり限界がある。タスクの独立した部分を見つけて横に広げ（並列化）、信頼性が必要な箇所に検証の関所を設け、単純作業には安いモデルを割り当てる。このGraph Engineeringの思考を身につけることで、単一モデルの性能の限界を超えた、信頼性が高く低コストなAIシステムを構築できる。
