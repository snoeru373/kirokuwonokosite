# グラフエンジニアリング入門 — RAGの限界とナレッジグラフの設計

**元ファイル群**: `Note Taking & Research Assistant Powered by AI .md`（原典）+ `(1)-(3)`（サブノート、すべて同じNotebook LMソース）

**出典**: https://notebooklm.google.com/notebook/b378c90e-602a-4238-95fa-d0b978191268（#1,#2,#3）、https://notebooklm.google.com/notebook/1cbc936e-3ad7-4e95-970e-4c213b2f9773（#4,#5,#6）

## 概要

このセクションでは、従来のRAGと線形エージェントの限界を克服する「グラフエンジニアリング」の設計パターンを解説する。Graph RAGは情報間の実在する因果関係を明示的に保存し、ハルシネーションを大幅に抑制しながら高精度な推論を実現する手法である。

## 1. 従来の手法の限界

### 線形エージェントの問題
従来のAIエージェントはステップ1→2→3…と直列処理するため：
- 不要な待ち時間が累積する
- コンテキストウィンドウが溢れてタスクを見失う
- 人間の操作（「調べて」「直して」「確認して」）自体がボトルネックになる

### 通常RAGの限界
通常の検索拡張生成はテキストの断片をキーワードマッチするだけで：
- イベント間の因果関係を見つけられない
- 複雑な質問でハルシネーションを起こしやすい
- 「もっともらしいけど間違っている」回答を生む

## 2. グラフエンジニアリングの基本構造

### ノード＝作業単位、エッジ＝依存関係
- **ノード**: 独立した「仕事をする場所」（エージェント・ツール・人間）
- **エッジ**: データの流れ（次のどこへ接続するか）
- ノード間の無意味な順序待ちは排除する

### ファンアウト・ファンイントポロジー
```
情報源1 ─┐
情報源2 ─┼─→ 並列処理（独立した複数のエージェント） ─┐
情報源3 ─┘                                              ├→ フォールディング（コードで重複排除・統合）
                                                          ↓
                                                      単一ノードで合成
```
- 独立した情報源やタスクを同時に処理
- 結果を非AIコードで整理統一
- 最後に1つのノードで統合

### コスト最適化
- 判定・推論が必要でするノード → 高性能モデル（高価）
- 単純な抽出・分類のノード → 低性能モデル（安価）
- ドータ平坦化・重複排除などのルーチン処理 → AIなしの通常コード

## 3. ナレッジグラフ構築（GraphRAG）9手順

1. **生ドキュメントの収集**: PDF、メール、レポート等あらゆるテキストを集める
2. **エンティティ抽出**: 人物・企業・製品・イベント・概念的実体をノードとして抽出
3. **関係性抽出**: エンティティ間のエッジ（〜は〜の開発者である、etc.）を抽出
4. **スキーマ構築**: エンティティの種類と関係性の種類を明示的に定義
5. **重複排除・正規化**: 「Microsoft Corp」と「MSFT」を同一実体として統合
6. **グラフDB保存**: Neo4j、Amazon Neptune、PostgreSQL等へ格納
7. **検索レイヤー構築**: ローカル検索＋グローバル検索の2層設計
8. **モデル接続**: Claude等をMCP/APIでグラフDBに接続（クエリ変換＋回答生成）
9. **継続的更新**: 新しい事実を「新規」「重複」「矛盾」「更新」「不確実」に分類

## 4. グラフ駆動の5大コアプロンプト

### ① 抽出プロンプト
文書からすべてのエンティティと関係性を返し、各エンティティに対して`canonical_name`,`type`,`description`,`source`を。各関係性に対して`source_entity`,`relation_type`,`target_entity`,`evidence`,`confidence_score`を返させる。

### ② 正規化プロンプト
2つのエンティティが「同一」「関連」「無関係」のいずれに該当するか分類。明確な証拠がない限り統合しない。

### ③ グラフクエリプロンプト
自然言語の質問をCypherやSPARQLに変換。**定義されたスキーマのみを使用**し、AIによるプロパティのでっち上げを禁止。生成クエリのロジック説明も付与。

### ④ 根拠回答プロンプﾄ
グフから検索した「ノード」「関係性パス」のみで回答生成。不確実な点は明示。相関因果の勝手な推論禁止。

### ⑤ グラフ保守プロンプト
新事実を既存と比較し分類。「明確な証拠がなければ既存事実を上書きしない」。

## 5. Graph RAG vs 通常RAG

| | 通常RAG | Graph RAG |
|---|---|---|
| ストレージ | テキストフラグメント | 明示的三重項（〜→開発者→〜） |
| 検索 | キーワードマッチ | ノード/エッジ追跡 |
| ハルシネーション | 依然として発生 | 事実ベースで大幅抑制 |
| コスト | — | 85%削減、正確性18%向上 |
| 複雑クエリ | 困難—テキスト断片の推論に依存 | 可能—グラフ上のパスを直接追跡 |

## 6. グラフを使う際の注意点

- 情報源が少ない場合→単純なRAGで十分
- 1つのAIに全部を任せるのは危険（自身エラーを見つけられない）
- 重要な処理は確実性のために固定、創造的な部分にAI裁量を付与
- スキーマ設計こそがハルシネーション対策の要
