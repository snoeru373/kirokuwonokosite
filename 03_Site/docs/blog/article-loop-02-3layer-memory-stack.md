# 毎回初対面のAIを「参謀」に変える — 3層記憶スタックの設計原則

## 出典

- Twitter: [@ObsidianOtaku](https://x.com/ObsidianOtaku/status/2072077831279181976)
- クリップ日時: 2026-07-15

---

## 要約（全文）

同じAIを毎日使っても毎回初対面になるのは、**プロンプトの問題ではなく「記憶設計がない」せい**。Obsidianに書いたノートをAIの会話に渡す仕組みがない限り、AIは「ゼロスタートの道具」でしかならない。3層の知識スタック（Obsidian = 記憶の地層・AIエージェント = 操作員・推論エンジン = 長文脈モデル）を統合すると、メモが蓄積されるだけでなく**使うほど精度が上がる設計**になる。

この記事はKarpathyのアイデアに影響を受けたClaude Codeチーム（[@ClaudeDevs](https://x.com/ClaudeDevs/status/2074208949205881033)）とObsidianOtaku（[@ObsidianOtaku/status/2072077831279181976](https://x.com/ObsidianOtaku/status/2072077831279181976)）の知見を統合し、日本のClaude Code + Obsidianユーザー向けに日本語で体系的に解説したものです。

---

## ① AIが毎回初対面になる理由

AIチャットのセッションは「ステートレス」に動いており、新しい会話を開いた瞬間、前回までの文脈はリセットされる。昨日の相談で積み上げた理解、先週まとめたプロジェクトの背景、半年かけて共有してきた業務の癖——これらはすべて次の会話に持ち越されない。

よくある対処として「プロンプトを磨く」方向があるが、それはそのセッションの出力を一時的に良くすることはできても根本的な問題は解消しない。プロンプトの問題ではなく**記憶設計の欠如という構造問題**。

---

## ② 知識スタックの3層設計

3つの層はそれぞれ異なる役割を持つ：

### 第1層：記憶の地層（Obsidian Vault）

自分の知識・作業ログ・参照情報を構造化して蓄積する場所。単なる保存庫ではなく、ノート同士がリンクで繋がった意味の構造を持つデータベースとして機能する。ObsidianはローカルのMarkdownファイルで動くため、AIエージェントが直接読み書きできる。

### 第2層：操作員（AIエージェント）

第1層のVaultを読み込み、必要なファイルセットを推論エンジンに渡し、処理結果をVaultに書き戻す役割。「読む・渡す・書き戻す」というサイクルを実行する存在。Claude Code、Codex、Hermes Agentなどがこれにあたる。

### 第3層：推論エンジン（長文脈モデル）

操作員から渡されたノートセット全体を一度に読み込み、タグ付け・構造化・リンク提案・要約を行う。**「一度にどれだけのVaultを読み込めるか」が精度を決める。** コンテキストウィンドウの大きさと精度の関係が決定的。

この3層が分離されたまま使われると記憶の断絶が起きるが、統合されるとフィードバックループが生まれる。書いたノートがAIに渡り、処理結果がVaultに戻り、次の作業の文脈になる。このサイクルが回るほど記憶は蓄積するし、精度も上がっていく（6ヶ月間続けると「一度も再設定せずに」自分の文体・判断傾向・タグ体系をAIが学習している状態になる）。

## ③ Obsidianを記憶の地層にする5フォルダ設計

| フォルダ | 誰が書くか | 役割 |
|---|---|---|
| Inbox/ | **人** | 一回目の記録。「後でAIが整理してくれる」という前提で自由に書き込み |
| Daily/ | **人** | 日次ログ。その日の作業・決定・気づき。低摩擦で書き続けることが重要 |
| Reading/ | **人** | 読んだ記事・本のハイライトや引用。人間が自由に書き込む |
| Projects/ | **AI** | 耐久性のあるアウトプット（整理・要約・リストラクチャリングの結果） |
| Reviews/ | **AI** | 週次・月次のサマリー（AIがDaily/とProjects/から生成） |

核心は「Inbox/Daily/Readingは人が書く。Projects/ReviewsはAIが処理する」という**役割分担**。フォルダに明確な役割がないとき、AIエージェントは「改善」ではなく「解釈」に処理を費やす。あるべきか判断することに時間がかかる。役割が明確なら即座に作業に入れます。

もう重要な原則がバックリンク活用です。Obsidianのバックリンク機能で双方向に繋いだノート同士がネットワークを形成し、AIにとって「意味のある文脈」になる。バックリンクで繋がったノードだけがAIにとりの読める記憶の地層になる。

## ④ エージェントがVaultを読み書きするループ設計

4ステップの基本：

1. **書き込む** — Inbox/またはDaily/にアイデアを書く（人）
2. **読み込む** — AIエージェントが指定フォルダを読む
3. **推論エンジンに渡す** — 関連ノートを選んで「これらをProjectsに照合してタグ付け・リンク提案」を実行
4. **Vaultに書き戻す** — モデルの処理結果を適切な場所に保存

このサイクルで重要なのは結果がVaultに残ること。AIチャットで「これを整理して」と聞いた返答は会話が終わると消える。エージェントがVaultに書き戻すループでは処理結果の一部になり、次の作業のコンテキストとして蓄積される。

---

## ⑤ コンテキスト射程距離が記憶設計の精度を決める

200K程度の射程ではタグ精度60%だが、1M以上の射程では90%になる（**差は30ポイント**）。なぜか？200Kでは一部のタグしか文脈に入らないので、残りは推測。1M+あれば Vault全体のタグ体系を一度に把握した上で taggingが可能。

vaultのlint（整合性チェック）は30回以上のツール呼び出しになる。200K帯では8〜9回目に最初の指示からドリフトする傾向がある。1M+射程であれば30回の呼び出し後も冒頭の指示を正確に保持できる。

---

## ⑥ 非同期スケジューリングで記憶が育つ

4つの自動化パターン：

| パターン | 内容 |
|---|---|
| **日次サマリー** | Daily/ノートを自動読み込み → Reviews/構造化サマリ |
| **週次レビュー** | Daily/ + Projects/の新着から週次サマリーを生成（週一度のlintで Vault構造を清潔に保つ） |
| **Vaultのlintスキャン** | 孤立したノード・構造上の問題を定期的に検出 |
| **夜間の変換** | Reading/ハイライト → アトミックノートに変換してリンク付け |

## ⑦ Claude CodeとObsidianで始める最小実践パス

完璧なVaultを作ろうとするのではなく「一つから始めて安定したら拡張する」戦略が一番。

1. VaultのパスをClaude Codeに渡す
2. **一つのフォルダ**（Inbox/）だけを指定 → 「新しいノートをProjectsに整理して」という一つのタスクを実行
3. Obsidianで出力を確認
4. 一つが安定したら次のフォルダ・次のタスクに拡充
